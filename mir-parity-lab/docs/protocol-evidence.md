# شواهد پروتکل و بازبینی سورس

این سند فقط چیزهایی را ثبت می‌کند که در سورس شاخه `mir` (کامیت `4d02c8f`) دیده شده‌اند. «دیده‌شده در سورس» با «مستند رسمی MIR» یا «تأیید سخت‌افزاری» یکی نیست.

## ۱. دامنه بازبینی

فایل‌های بازبینی‌شده:

- `app/Src/Device/DeviceSession.cs`
- `app/Src/MirUsb.cs`
- `app/Src/Device/PacketDecoder.cs`
- `app/Src/Expiration.cs`
- `app/Src/SpiroAnalysis.cs`
- `app/Src/BestValues.cs`
- `app/Src/SessionBestValues.cs`

هدف: تشخیص پارامترهای قابل خواندن، آفست‌ها، واحدها، انتساب مانور، ریسک داده کهنه و تفاوت منحنی ذخیره‌شده با منحنی بازسازی‌شده.

## ۲. فریم‌بندی USB

در `MirUsb.ReadBlock`:

```csharp
byte[] head = Get(cmd, 4);
int len = (head[0] << 24) | (head[1] << 16) | (head[2] << 8) | head[3];
if (len > 0 && len <= 200000) {
    byte[] data = BulkRead(len, 3000);
    if (data != null && data.Length == len) return data;
}
```

نتیجه:

- `cod_LAST` و `cod_CURVE` هر دو طول ۴ بایتی big-endian دارند.
- payload جداگانه bulk خوانده می‌شود.
- حداکثر ۲۰۰۰۰۰ بایت در سورس پذیرفته می‌شود.
- بسته زنده ۳ بایت است: `type`, `raw_hi`, `raw_lo`.

## ۳. توالی خواندن نتیجه

`ReadResults` قبل از خواندن بلوک، این شرایط را بررسی می‌کند:

- `captureSequence > 0`
- `captureSequence == _activeCaptureSequence`
- `_captureCompletedUtc != DateTime.MinValue`
- نتیجه قبلی برای همان capture خوانده نشده باشد
- تأخیر خواندن بین ۰ و ۱۰ ثانیه باشد

سپس:

- `ReadBlock(0xA2, 21, 100)`
- اگر طول < `0x1C`: `truncated_cod_LAST_block`
- اگر بلوک byte-identical با بلوک قبلی و همان سریال باشد: `stale_duplicate_cod_LAST_block`
- در غیر این صورت فیلدها خوانده می‌شوند و sanity check انجام می‌شود.

### ریسک باقی‌مانده

رد بلوک تکراری فقط byte-identical را می‌گیرد. اگر دستگاه یا نرم‌افزار دیگری بلوک قدیمی را با حتی یک بایت تغییر دهد، ابزار نمی‌تواند کهنه بودن را از خود بلوک تشخیص دهد. شناسه مانور در سطح دستگاه وجود ندارد.

## ۴. `cod_LAST`: چیدمان مشاهده‌شده

```text
0x00 .. 0x09  Unknown
0x0A .. 0x0B  Quality/reserved (raw only; Unknown)
0x0C .. 0x0F  Unknown
0x10 .. 0x11  FVC      u16_be / 100  L
0x12 .. 0x13  FEV1     u16_be / 100  L
0x14 .. 0x15  PEF      u16_be / 100  L/s
0x16 .. 0x19  Unknown
0x1A .. 0x1B  FET      u16_be / 100  s
0x1C .. 0x4F  Unknown
0x50 .. 0x51  PEF time u16_be / 100  s   (only if length >= 0x52)
0x52 .. end   Unknown
```

- حداقل طول مشاهده‌شده: `0x1C`.
- `PEF time` فقط با طول ≥ `0x52` خوانده می‌شود.
- `Quality` فقط با طول ≥ `0x0C` خوانده می‌شود و در سورس صریحاً `unverified; diagnostic only` است.

## ۵. اعتبارسنجی سورس

`DeviceSession.ReadResults` این محدوده‌ها را اعمال می‌کند:

```text
FVC   >= 0.05 && <= 12
FEV1  >= 0.05 && <= FVC + 0.05
PEF   > 0     && <= 20
FET   > 0     && <= 30
PEF time > 0  && <= FET + 0.05
```

اگر چهار فیلد اصلی نامعتبر باشند، بلوک `cod_LAST_required_core_field_missing_or_outside_supported_ranges` می‌گیرد و به‌عنوان نتیجه بالینی استفاده نمی‌شود. این محدوده‌ها برای رد داده مخدوش است، نه اثبات صحت فیزیولوژیک.

## ۶. `PacketDecoder` و فرمول علامت

مسیر پردازش:

- `0x20`: مقدار volume-like را جایگزین `_volume` می‌کند.
- `0x30`: حجم را با `Math.Sign(flow) * step` جمع می‌زند.
- `0x40`: حجم را با `flow * step` جمع می‌زند.
- فرمول جریان: `(raw < 0x8000 ? raw : raw - 65535) / 100.0`.

اختلاف یک‌واحدی با مکمل دو استاندارد در شاخه منفی وجود دارد. این ابزار آن را به‌عنوان «شاهد سورس، تأییدنشده» نگه می‌دارد. برای مقادیر مثبت تفاوتی ندارد؛ برای مقادیر منفی نباید بدون آزمون واقعی تفسیر شود.

## ۷. `cod_CURVE`

- در `DeviceSession.ReadCurve` فقط خوانده و لاگ می‌شود.
- هیچ decoder ای در سورس بررسی‌شده برای آن پیدا نشد.
- بنابراین «منحنی ذخیره‌شده دستگاه» و «منحنی بازسازی‌شده از بسته‌های زنده» دو چیز متفاوت‌اند.
- ابزار `cod_CURVE` را خام نگه می‌دارد و هیچ ادعای تطابق با آن نمی‌کند.

## ۸. محاسبه نرم‌افزاری

`SpiroAnalysis.cs` مقادیر FVC/FEV1/PEF/FET را از منحنی محاسبه می‌کند. در این ابزار، بازسازی مستقل با روش `independent_positive_flow_integration_v1` انجام می‌شود:

- فقط بسته‌های flow مثبت/معتبر
- گام زمانی از `step` یا زمان بسته
- انتگرال‌گیری مستقل
- برچسب همیشگی `Software-calculated`
- هرگز جای `Device-reported`

این بازسازی برای بررسی ساختاری و مقایسه پژوهشی است، نه بازتولید الگوریتم MIR یا SpiroLab.

## ۹. `BestValues` و تفکیک منبع

در `BestValues.cs`:

- فیلدهای دستگاه با `cod_LAST@0x10`، `0x12`، `0x14`، `0x1A` و دقت `0.01` ثبت می‌شوند.
- `DeviceValue` فقط وقتی استفاده می‌شود که دستگاه verified باشد.
- `Software` برای مقادیر محاسبه‌شده است.
- `LegacyDeviceValue` مسیر قدیمی/غیرverified است.

این ساختار نشان می‌دهد خود SpiroLab هم بین «خوانده‌شده از دستگاه» و «محاسبه‌شده» تفکیک قائل شده است. ابزار Parity Lab همین تفکیک را سخت‌گیرانه‌تر و با شش وضعیت اعمال می‌کند.

## ۱۰. نتیجه بازبینی

### آنچه با شاهد سورس قابل ادعاست

- `cod_LAST` طول‌دار است و حداقل `0x1C` بایت دارد.
- پنج مقدار عددی در آفست‌های `0x10`, `0x12`, `0x14`, `0x1A`, `0x50` با `u16_be / 100` خوانده می‌شوند.
- `0x0A` یک فیلد ناشناخته/رزرو است و نباید بالینی استفاده شود.
- `cod_CURVE` در سورس decoder ندارد.
- انتساب مانور سخت‌افزاری نیست و به توالی/زمان/سریال/تک‌خواندن وابسته است.

### آنچه هنوز اثبات نشده

- معنا و مبدأ `PEF time`.
- معنای `0x20` و `0x01` در همه firmwareها.
- نگاشت دقیق بایت‌های ناشناخته.
- صحت فرمول منفی.
- برابری مقادیر decoded با نمایشگر/پرینت/نرم‌افزار رسمی MIR.
- رفتار در firmwareها و مدل‌های مختلف.
- هرگونه BTPS، کالیبراسیون یا اعتبار بالینی.

## ۱۱. مرز ایمنی این فاز

کد Parity Lab هیچ transport USB ندارد. فقط فایل می‌خواند. بنابراین در این فاز امکان ارسال فرمان، تغییر firmware/calibration/settings/memory/record/serial/communication/time وجود ندارد. این یک محدودیت عامدانه است، نه ادعای پوشش کامل فاز ۲.
